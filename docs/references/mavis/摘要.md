## 这份资料解决什么问题

mavis 是基于 LLM 与多智能体协同的天文可视化智能系统，以 WorldWide Telescope（WWT）为核心渲染平台，覆盖天文数据查询、观测计划制定、天象计算、数据下载与处理、直至最终可视化呈现的完整链路。系统将数十个天文工具（Astropy、Skyfield、astroquery 等）封装为 LLM 可调用的能力单元，通过动态检索与递归任务编排，使自然语言指令能够驱动真实的天文计算与可视化流程。对于同样需要连接天文数据源并产出可视化结果的团队而言，mavis 提供了一套从工具封装、任务分解到渲染集成的可参考范式。

## 与当前项目的可能关联

可研究其与 `services/data_pipeline`、`services/graph_pipeline` 的潜在关联：天文工具的结构化描述方式、复杂任务的递归分解，以及 WWT 可视化后端的集成边界。这里只记录比较方向，不表示本项目已选用其接口、编排或渲染方案。

## 代码结构概要

mavis 原始代码包体积约 372MB，包含 JPL 星历表文件与 20 余个 benchmark 任务（含 xlsx 数据与参考图像）。考虑到体积与项目聚焦，已精简为 11 个 API JSON 文档保留在本目录的 `api/` 下，覆盖 mavis 调用的全部天文工具与 WWT 渲染接口。

- `astropy.json`：Astropy 天文库 API，涵盖坐标转换、单位处理、时间计算、物理常数等。
- `getData.json` / `getData2.json`：天文数据获取 API，封装 astroquery 的 Simbad、VizieR 等查询接口。
- `photutils.json`：PhotUtils 测光工具 API，用于天体测光与图像处理。
- `skyfield.json` / `skyfield2.json` / `skyfield3.json`：Skyfield 天文计算 API，涵盖卫星轨道、行星位置、四季与月相计算等。
- `wwt_agent.json` / `wwt_agent1.json` / `wwt_agent2.json` / `wwt_agent4.json`：WWT Agent API，控制可视化渲染、图层管理、时间设置与标注叠加。

## 论文核心技术

论文（`docs/references/papers/mavis-天文可视化工具.pdf`）提出三项核心技术。第一项是动态 RAG 工具调用：系统从 93 个天文查询工具中，通过检索增强生成动态匹配当前任务所需的工具子集，而非将全部工具塞入上下文，有效控制了 token 消耗与选择精度。第二项是反向递归多智能体编排：一个中心调度器负责全局协调，每个终端目标 Agent 对应一个最终任务；当 Agent 发现自身缺少前置数据时，递归地向下分配子 Agent 获取缺失数据，形成"工具选择 → 缺失数据识别 → 前置 Agent 分配"的循环，直到所有依赖满足后才回溯执行。第三项是 WWT 五层解耦架构，自底向上为数据层、决策过程可视化层、多智能体协同调度层、感知层与空间交互层，各层职责清晰、可独立替换。

## 我们可以借鉴什么

mavis 的 API JSON 以 `工具名`、`导入模块`、`作用`、`参数`、`返回值` 描述工具，可作为比较机器可读工具契约的一份样本。其 `divide_task` 机制让子任务携带输入与预期输出，可用于研究跨文献流程的拆分方式；`visual_suggestion` 也可用于比较结构化结果与呈现建议的边界。这些做法均不能直接进入生产实现：需要先与 Pydantic Contract、Evidence 规则、后端信任边界和自动化测试对齐。

## 注意事项

JPL 星历表文件（`de421.bsp`，约 16.8MB）未包含在当前仓库中；若后续 `data_pipeline` 需要调用 Skyfield 进行行星位置或天象计算，需从 NASA JPL 官网下载对应星历表并放入指定路径。WWT 平台原生依赖 Windows 环境，亦提供 Web 版本，服务器端部署需额外评估渲染能力与兼容性。原始 benchmark 任务数据（20+ 个，含 xlsx 数据文件与参考图像）在精简时未保留，如需参照其任务设计或评测口径，可从原始 mavis zip 包中提取。此外，mavis 的工具封装与 WWT 调用均在本地执行，与本项目"前端不直连外部数据源"的科研可信红线一致——我们应同样确保所有天文工具调用经由后端封装，前端仅消费结构化结果。
