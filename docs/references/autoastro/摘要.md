## 1. 研究主题

AutoAstro 探索使用 LLM 组织天文数据分析任务，包括研究目标解析、任务推荐、数据交叉匹配、分析执行、可视化和复杂任务分解。

其价值主要在于观察：

- 自然语言研究目标如何转化为受控任务；
- 数据交叉匹配与分析工具如何封装；
- 复杂任务如何分解、检测失败和重新规划；
- 自动分析系统如何设计评测样例和效率指标。

这些方向与星文智析的数据 Pipeline 和 Research Contract 有概念关联，但领域模型、权限、Evidence 和版本规则必须按当前项目重新设计。

## 2. 资料结构

选定代码位于 `code/`，包含：

- 主执行与计划生成；
- 数据加载、交叉匹配和分析；
- 工具封装与模型调用；
- 错误纠正、代码执行和任务记忆；
- Prompt 与评测相关逻辑。

文件清单只说明调研覆盖，不表示这些模块将原样进入生产系统。

## 3. 可研究的设计问题

| 主题                | 对本项目的研究问题                                                   |
| ------------------- | -------------------------------------------------------------------- |
| Task recommendation | 如何让自然语言意图先形成可编辑 ResearchContractDraft，而不是直接执行 |
| Cross-match         | 如何定义对象标识、匹配条件、冲突和 Evidence                          |
| Tool configuration  | 如何通过受控 Adapter 与 Schema 调用数据工具                          |
| Task decomposition  | 哪些逻辑属于 Workflow，哪些属于 Pipeline 内部步骤                    |
| Error correction    | 自动 retry、用户 retry、revision Run 应如何分离                      |
| Evaluation          | 如何构建覆盖字段、冗余、耗时和成功率的固定 Benchmark                 |

## 4. 不可直接采用的内容

- 第三方 Prompt、模型配置和调用代码；
- 任意代码执行或自动生成分析脚本的权限模型；
- 未经过许可、依赖和安全审查的数据集或模型资产；
- 将任务记忆、历史输出或模型自由文本直接作为科研事实；
- 只更换 endpoint / model name 就认为完成模型迁移；
- 论文报告的指标直接作为本项目性能承诺。

## 5. 采用门禁

参考思想进入实现前必须回答：

1. 是否符合 Case / Field Manifest 和 ResearchContract？
2. 输入输出是否通过当前 Schema 并形成 SourceSnapshot / Evidence？
3. 是否保持 Workflow、Pipeline 和 Adapter 边界？
4. 是否记录 producer、版本和 input/output hash？
5. 失败、权限和资源限制是否可测试？
6. 是否在固定主案例 Benchmark 上优于更简单方案？

未通过这些门禁的代码只保留为调研样例。
