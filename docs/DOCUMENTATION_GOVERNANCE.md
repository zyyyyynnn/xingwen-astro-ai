# Documentation Governance

| 元数据 | 值 |
| --- | --- |
| Status | Accepted |
| Authority | 文档层级、职责、生命周期与质量门禁 |
| Applies to | 仓库内全部 Markdown、生成文档与参考资料 |

本文定义星文智析文档体系的组织规则。具体产品、架构或工程事实仍由对应专项文档维护；本文不重复这些事实。

## 1. 文档层级

文档按权威性分为五层：

| 层级 | 类型 | 作用 | 是否可作为实现依据 |
| --- | --- | --- | --- |
| L0 | 入口 | 说明项目是什么、当前状态和如何定位文档 | 仅作导航与摘要 |
| L1 | 核心规范 | 冻结产品范围、系统不变量、接口、数据和工作流 | 是 |
| L2 | 专项规范 | 细化前端、视觉、AI、测试、安全和部署 | 是，限所属范围 |
| L3 | 执行治理 | Roadmap、Backlog、Acceptance、Review、协作与交接 | 是，限计划和流程 |
| L4 | 参考与归档 | 赛题原文、第三方资料、历史简报、示例代码 | 否，除非被规范文档明确采纳 |

权威性冲突时按以下顺序处理：

1. 当前 Issue / PR 已明确批准的范围；
2. L1 核心规范；
3. L2 专项规范；
4. L3 执行治理；
5. L0 摘要；
6. L4 参考与历史资料。

发现冲突不得自行选择“看起来更新”的版本。应修正低权威文档，或通过 ADR / Issue 修改高权威事实。

## 2. 唯一事实来源

同一事实只能有一个完整正文来源。其他文档可以：

- 用一至三句话摘要；
- 链接唯一正文；
- 说明该事实如何影响本文件范围。

其他文档不得：

- 复制完整枚举、状态机、技术栈表或验收清单；
- 维护同一流程的第二套步骤；
- 用不同术语重新描述同一领域对象；
- 把历史实现写成目标架构，或把目标架构写成已实现。

主要事实来源见 [docs/README.md](README.md)。

## 3. 标准元数据

规范性文档在标题后使用简短元数据表：

```markdown
| 元数据 | 值 |
| --- | --- |
| Status | Proposed / Accepted / Implemented / Superseded / Archived |
| Authority | 本文件唯一负责的事实范围 |
| Implementation | Current / Pending / Partial / Implemented（需要时） |
```

字段规则：

- `Status` 描述文档决策状态，不等同于代码完成状态。
- `Implementation` 只在文档描述尚未全部落地的目标时使用。
- 当前与目标同时存在时，正文必须明确 Current / Target / Migration Boundary。
- 参考资料使用 `Status: Reference`；历史资料使用 `Status: Archived`。

## 4. 文档生命周期

| 状态 | 含义 | 允许用途 |
| --- | --- | --- |
| Proposed | 尚待确认 | 讨论和评审，不作为默认实现依据 |
| Accepted | 已确认 | 可驱动 Issue 与实现 |
| Implemented | 已由代码和验证证明 | 当前运行事实 |
| Superseded | 已被新决策取代 | 仅保留历史和迁移解释 |
| Archived | 不再维护 | 不作为实现依据 |
| Reference | 外部或辅助资料 | 仅供研究和比较 |

状态变化必须在 PR 中说明替代关系和实现影响。删除文档前确认不存在有效链接和独有事实。

## 5. 文档职责边界

### 5.1 入口文档

- `README.md`：项目定位、当前状态、快速启动、最小文档入口。
- `docs/README.md`：完整文档地图、权威层级和任务定位。

入口文档不维护完整技术栈、状态机、API、视觉规则或验收清单。

### 5.2 产品与设计

- `PRD.md`：用户、问题、产品范围、主流程、成功指标和非目标。
- `DESIGN.md`：设计原则、体验域、交互模型和专项设计入口。
- `docs/design/*`：视觉语言与具体工作台交互。

### 5.3 架构与契约

- `API_CONTRACT.md`：HTTP 资源、传输结构、错误和授权语义。
- `DATA_MODEL.md`：领域实体、字段和不变量。
- `WORKFLOW_DESIGN.md`：Run 状态、步骤、事件、取消、重试和派生。
- `DATA_VERSIONING.md`：ArtifactVersion、缓存、修订、分享和保留。
- `MODULES.md`：跨模块职责、输入输出和依赖方向。
- `DECISIONS.md`：不可逆或高成本技术决策及其历史。

### 5.4 工程与质量

- `TEST_STRATEGY.md`：测试分层、数据等级、测试环境和 CI 测试策略。
- `ACCEPTANCE.md`：里程碑与发布退出标准。
- `REVIEW_CHECKLIST.md`：单个 PR 的审查清单。
- `RISK_REGISTER.md`：仍然有效的风险、影响和缓解措施。
- `SECURITY.md`：安全要求；`DEPLOYMENT.md`：环境和发布操作。

## 6. 合并、拆分与归档标准

### 应合并

- 两份文档的受众、更新触发和主要事实相同；
- 一份文档超过一半内容只是另一份的摘要；
- 两份文档需要在同一次变更中始终同步。

### 应拆分

- 单份文档同时服务不同受众，且更新频率明显不同；
- 规范正文与操作手册混在一起；
- 单个章节形成独立、稳定且可复用的事实域；
- 文件过长导致局部修改难以审查，但拆分后仍能保持明确索引。

### 应归档

- 只描述历史团队、旧技术栈、旧预算或旧阶段状态；
- 已被 ADR 或新规范取代；
- 对当前实现没有操作价值，但仍需保留历史证据。

归档文件放入 `docs/archive/`，必须注明时间范围和替代文档。

## 7. 命名、链接与索引

- 文件名使用稳定、可预测的英文大写主题名或目录级 `README.md`。
- 不在标题中写“最终版”“最新版”等会失效的词。
- 相对链接优先；链接文本说明目标文档职责，而不是只写“点击这里”。
- `docs/README.md` 是完整索引；根 README 不复制完整索引。
- 参考资料和生成物不得出现在核心规范表中，除非明确标记类型。
- 文档移动必须在同一 PR 更新全部链接。

## 8. 编写质量要求

关键规范必须做到：

- 开头说明 Authority、适用范围和不负责的内容；
- 使用统一领域术语，不创造展示同义词替代契约字段；
- 规则可验证，避免“合理”“完善”“尽量”等无验收含义表述；
- 示例与规范明确区分，示例不得扩展产品承诺；
- 枚举和状态只在唯一事实源完整定义；
- 当前、目标、历史和参考资料明确分层；
- 不写个人电脑路径、临时分支、易失价格或未经验证的当前状态；
- 不包含密钥、私有 token、受限全文或模型私有推理。

## 9. 变更门禁

文档 PR 至少执行：

- `git diff --check`；
- `python scripts/check_foundation.py`；
- Markdown 标题、代码块、表格和相对链接检查；
- Mermaid 语法检查（存在 Mermaid 变更时）；
- 术语扫描：Current / Target / Pending、Fixture / Live / Cached、Run / ArtifactVersion；
- 索引覆盖检查：新增、移动或删除文档已同步 `docs/README.md`；
- 唯一事实源检查：没有新增大段重复正文。

具体 PR 审查项见 [Review Checklist](quality/REVIEW_CHECKLIST.md)。
